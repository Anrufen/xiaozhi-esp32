# Spec — 1.85C 第三方服务（Navidrome / Beszel）可配置化

**Status:** ready-for-agent
**Scope boundary:** 仅 Waveshare ESP32-S3 Touch LCD 1.85C 板型。不得修改核心层（application、protocols、audio、通用 display）。

## Problem Statement

作为这台设备的持有者，我把 Navidrome 音乐服务和 Beszel VPS 监控服务的地址、账号、密码直接写死在固件源码里。结果是：

- 换一台音乐服务器（地址变了）就必须改 C++ 代码并重新编译。
- 想把固件分享给别人，对方无法连接自己的服务；而且固件里带着我的真实密码，**现在的发布包不能对外分发**。
- 通过 MCP 工具设置的 Navidrome 地址只存在内存里，设备重启就回到写死的旧值。
- Beszel 的地址、账号、密码、刷新间隔、轮播间隔完全没有修改入口。
- 没配置服务时，设备仍会不停重试请求并显示示例数据，行为不可理解。

## Solution

把两个服务的连接参数变成"配置"而不是"代码"：

- **运行期配置存放在设备 NVS 中**，重启不丢，是唯一生效来源。
- **编译期默认值来自 Kconfig**（`idf.py menuconfig`），出厂默认**凭据为空**。
- 取值规则固定为：**NVS 有值用 NVS，否则用 Kconfig 默认值。**
- 通过现有 MCP 工具修改并写入 NVS。
- 两个服务都可以在编译期整体关闭。
- 未配置时，对应页面明确显示"未配置"，且不发起网络请求。
- 提供可分发构建流程，并能自动验证产物中不含个人凭据。

## User Stories

1. 作为设备持有者，我想只改一个地址就让设备连到新的 Navidrome 服务器，以便换机器后不用改代码。
2. 作为设备持有者，我想通过 MCP 工具设置 Navidrome 地址、账号、密码，以便在不重新烧录的情况下切换服务。
3. 作为设备持有者，我想让设置过的 Navidrome 参数在断电重启后依然有效，以便不用每次开机重新设置。
4. 作为设备持有者，我想通过 MCP 工具设置 Beszel 的 Hub 地址、账号、密码，以便监控我自己的 VPS 集群。
5. 作为设备持有者，我想修改 Beszel 的数据刷新间隔和轮播切换间隔，以便在流量和实时性之间取舍。
6. 作为设备持有者，我想在 menuconfig 里集中看到所有服务相关的编译期选项，以便一次配好后直接打包。
7. 作为固件分发者，我想让默认构建产物里不包含任何账号密码，以便安全地发给他人。
8. 作为固件分发者，我想有一个自动检查，能发现固件镜像里残留我的个人凭据，以便避免误发。
9. 作为固件分发者，我想把"个人默认值"放在不入库的本地覆盖文件里，以便自用构建和分发构建互不污染。
10. 作为接收固件的朋友，我想在没有任何配置时看到清晰的"未配置"提示，以便知道下一步该做什么。
11. 作为接收固件的朋友，我想设备在未配置服务时不发网络请求，以便不浪费电和带宽。
12. 作为接收固件的朋友，我想用 MCP 工具设置自己的服务后立刻生效，不必重启。
13. 作为设备持有者，我想关闭不需要的服务（比如不用音乐），以便省下 flash 与内存。
14. 作为设备持有者，我想输入地址时末尾带不带 `/` 都能正常工作，以便减少配置失误。
15. 作为设备持有者，我想对非法输入（空地址、缺协议头）得到明确的拒绝，而不是写入后默默失败。
16. 作为设备持有者，我想从旧固件升级后仍能继续使用我的服务，以便升级不中断使用。
17. 作为设备持有者，我想日志里不出现任何密码，以便串口日志可以安全地贴出来求助。
18. 作为开发者，我想用同一份规则解析"NVS 优先于 Kconfig 默认值"，以便行为可以被宿主机测试验证。
19. 作为开发者，我想让设置密码的 MCP 工具返回值和日志不回显密码，以便避免泄露。
20. 作为开发者，我想未配置、认证失败、网络不可达三种情况在界面上能区分，以便排查问题。

## Implementation Decisions

**配置模块（新增，板级私有，不依赖 LVGL）**
- 一个独立的"服务配置"模块，负责：从 NVS 读取、回退到 Kconfig 默认值、写入 NVS、规范化地址、判断"是否已配置"。
- 存储后端通过一个很小的键值接口注入，生产环境对接仓库已有的 `Settings` 封装，测试环境用内存实现。**不新造 NVS 封装。**
- 取值优先级：NVS > Kconfig 默认值。**只有这一个数据源规则，不引入其他入口并存。**
- 地址规范化：去除首尾空白与末尾 `/`；要求以 `http://` 或 `https://` 开头；空值视为"未配置"。
- "已配置"判定：Navidrome 需要地址、账号、密码都非空；Beszel 需要地址、账号、密码都非空。

**NVS 约定（持久化 API，一经发布不得改名）**
- 命名空间：`waveshare185c`（≤15 字符）
- 键：`navi_url`、`navi_user`、`navi_pass`、`bsz_url`、`bsz_user`、`bsz_pass`、`bsz_fetch_s`（整型，秒）、`bsz_rotate_s`（整型，秒）
- 键均 ≤15 字符。

**Kconfig**
- 配置项加在仓库已有的集中式 Kconfig 里，挂在 1.85C 板型的依赖下。**不存在板级 `Kconfig.board` 机制，不要新建。**
- 每个服务一个使能开关 + 对应字符串项；Beszel 另有刷新间隔（默认 15）和轮播间隔（默认 5）。
- 所有凭据类字符串项默认值为空。地址类默认值也为空。
- 开关关闭时，对应的源码段通过条件编译整体剔除，页面和 MCP 工具一并不注册。

**MCP 工具**
- 保留现有 Navidrome 设置工具，行为变为"写入 NVS 并立即生效"，并扩展为可设置账号与密码。
- 新增 Beszel 设置工具，覆盖地址、账号、密码、两个间隔。
- 所有设置类工具对非法输入返回错误，对密码字段不回显。
- 设置 Beszel 参数后需丢弃已缓存的登录 token，并触发一次重新拉取。

**运行时行为**
- 业务代码从配置模块读取当前值，不再持有写死的初值。
- 未配置时：不创建网络任务、不发请求；对应页面显示"未配置"文案；不展示示例数据。
- 已配置但失败时：界面区分"认证失败"和"网络不可达"，并沿用现有的退避/间隔，不新增无限快速重试。
- 日志中不得输出密码；流媒体地址里含密码的日志必须脱敏。
- 现有内置的示例曲目列表（含个人曲库的曲目 ID）必须移除，改为空列表加"未配置/无曲目"状态。

**可分发构建**
- 个人默认值放在**不入库**的本地覆盖文件里，通过构建参数叠加；不得编辑 `sdkconfig*`。
- 提供一个检查步骤：对生成的固件镜像做字符串扫描，命中给定的"禁用字符串列表"即失败。该列表由使用者在本地提供，不入库。
- 发布包的 README 同步修正，说明配置优先级和首次配置方法。

**升级兼容**
- 老设备 NVS 里没有这些键。升级到新固件后，若 Kconfig 默认值为空，服务会变成"未配置"。
- 自用构建通过本地覆盖文件提供个人默认值，因此自用设备升级后行为不变。
- 分发构建没有个人默认值，朋友设备首次需要通过 MCP 配置，这是预期行为。

## Testing Decisions

- **好测试的标准：** 只验证外部可观察行为（给定 NVS 内容和默认值，得到什么生效配置；给定输入，被接受还是拒绝），不测内部数据结构。
- **最高 seam：** 配置模块的"解析生效配置 + 规范化 + 校验"。这是唯一新增的测试 seam，因为它不依赖 LVGL 和 ESP-IDF。
- **测试形态：** 宿主机 C++ 单元测试，由现有 `scripts/tests` 下的 Python `unittest` 编译并运行，纳入 `python3 -m unittest discover -s scripts/tests -v`。先例：该目录已有 `test_ogg_demuxer.py` 这类针对 C++ 逻辑的宿主机测试，沿用其方式。
- 必测用例：NVS 优先于默认值；NVS 为空时回退默认值；地址规范化（空白、尾部斜杠、缺协议头、空值）；"已配置"判定矩阵；整数键的缺省与越界（间隔 ≤0 或过大时回退默认值）。
- UI 渲染、HTTP、流媒体：**不做自动化测试**，通过构建通过、串口日志核对和真机冒烟验证，并在最终报告中明确"仍需真机验证"。
- 构建验证：板级变更需构建受影响的 1.85C 变体；Kconfig 改动需对"两个服务全开"与"全关"两种组合各构建一次。

## Out of Scope

- 配网页面（Captive Portal/WebUI）增加扩展配置标签页——会触碰核心配网代码，另议。
- 把 `custom_lcd_display` 大规模拆分为多文件目录。
- 抽取 `BeszelClient` / `NavidromeClient` 为独立服务类（后续可做，应先有本 spec 的配置模块和测试作为保护）。
- 天气功能的配置化。
- Navidrome 改用 token+salt 认证、Beszel 改用 HTTPS（见 Further Notes）。
- 任何对其他板型的改动。

## Further Notes

- 现状里 Navidrome 以明文 `p=` 参数在 URL 查询串里传密码，并通过 HTTP 传输；Subsonic 支持 token+salt 方式，头文件中已有相关字段但未使用。这是独立的安全改进，建议在本 spec 之后单独立项。
- 之前草稿里"流媒体任务在 Core 1"的说法不成立：现有任务通过 `xTaskCreate` 创建，没有核心绑定，优先级为 1。本 spec 不改变任务模型。
- 当前已烧录的设备与已生成的 `dist/` 发布包含有真实凭据，在本 spec 的"可分发构建"完成之前，**不要对外分发**。
- 任务所用 NVS 键名与命名空间一旦发布即成为持久化 API，修改需要提供迁移。
